# 4b 走査線

Console138K／NESの実機確認済みtag `crt-stage4a-hw-20261103` を基準に、走査線の明暗処理とOSD2の操作を追加する。実装・検証・commitは水平ぼかしの4aと分ける。

## この段階の設計決定

既存の224行→720行の拡大位相に基づき、各元走査線に対応する3〜4本の表示行のうち、最後の1本だけを暗くする。単にHDMIの偶数・奇数行を選ぶ方式は使わない。

既存scalerの `ycnt` は表示行ごとに224を加算し、720で折り返す。ゲーム表示中に `ycnt >= 496`（720−224）となる行が、次の表示行で元走査線を進める直前の行である。この情報を `source_line_end` としてfilterへ渡す。追加の独立した行counterを持たず、既存のframe開始時の位相初期化に従う。

例えば先頭の表示行0〜3が元走査線0に対応し、その最後の行3を暗くする。続く表示行4〜6では行6、表示行7〜9では行9を暗くする。720行中の暗い行は224行になり、frameを跨いで模様がずれない。この位相生成は今回のNES scaler用であり、他coreの解像度へ適用する場合は別途対応する。

各RGB成分の入力値をCとすると、暗い行の出力は次のとおり。明るい行はそのまま通す。

| SCANLINE | 暗い行のRGB係数 | 整数演算 |
| --- | --- | --- |
| OFF | 1 | C |
| WEAK | 7/8（87.5%） | floor((7C + 4) / 8) |
| STANDARD | 3/4（75%） | floor((3C + 2) / 4) |
| STRONG | 1/2（50%） | floor((C + 1) / 2) |

係数は8 bit RGB値への倍率であり、測光上の輝度倍率ではない。gamma変換は追加せず、最近整数へ丸め、ちょうど半分は切り上げる。中間和は11 bitで保持する。黒は0のままで、白255の暗い行はWEAKで223、STANDARDで191、STRONGで128になる。これらの係数と1行の暗い帯を4bの初期方式として決定し、実機の見え方で調整の必要性を判断する。

## 映像経路と互換性

処理順序は「色変換・拡大→水平ぼかし→走査線→OSD合成→HDMI」とする。OSD文字・背景領域へ走査線を掛けない。ぼかしの加算は同じ整数結果になる順序へ整理する。

初回の配置配線では色変換・ぼかし・減光を通る経路が長く、setup違反1,961件、hold違反0件となった。処理を一部分割した版でも、ぼかし単体の経路にsetup違反508件が残った。これらのimageは実機へ反映せず、失敗時のreportとsourceを別途保存した。

修正版では色変換後とぼかし結果にRGB888のregisterを追加し、ぼかしを有効にした場合は常にこの保持段を使う。追加memoryは2画素分のregisterであり、frame buffer・行bufferは追加しない。

| 有効な効果 | memory先読み | 処理内部の保持 |
| --- | --- | --- |
| なし | なし | なし |
| ぼかしのみ | 3 pixel clock | 色変換RGB＋中央画素保持＋ぼかし結果 |
| 走査線のみ | なし | 追加保持を使わない |
| ぼかしと走査線 | 3 pixel clock | 色変換RGB＋中央画素保持＋ぼかし結果 |

ぼかし有効時は表示中の列の3 clock後に対応するNES列を既存scalerの位相から求め、ぼかしの端判定も1画素先へ進める。行境界はゲーム表示前の余白で処理を準備する。走査線の明暗判定は最終表示画素の位相を使う。明るい行も暗い行も同じ保持段を通し、行ごとに遅延を変えない。先読みと保持を相殺するため、最終RGB、OSD、HDMIの位置は4aから変えない。

減光の入力は、走査線単体なら元のRGB、ぼかしを使う場合はregisterに保持したぼかし結果から選ぶ。未registerのぼかし結果を最終RGBへ接続せず、長い経路がtiming解析で残ることを防ぐ。ぼかし有効時のmemory参照は4aより2 pixel clock早くなるため、書き換えと重なる場合の動く場面の見え方も実機確認対象とする。

SCANLINEがOFFなら、ぼかしの演算と画素位置は4aと同じになる。ぼかし有効時にはmemory参照時刻が変わるため、4aとのbit一致は書き換えを止めた参照映像で確認する。CRT ENABLEがOFFなら両方の効果をbypassし、RGBとmemory読み出し時刻を従来どおり維持する。ぼかしがOFFの場合も、走査線だけを有効にして従来の読み出し時刻を維持する。

`core_config` のbit 16は共通の有効flag、bit 18:17はぼかし、bit 20:19は走査線の強度0〜3として使う。設定転送、frame境界での一括反映、適用後のFRAME ACKは既存方式を継続する。保存はまだ行わず、新しいゲームで3項目をOFFへ初期化する。

## 能力通知とOSD2

NESは `OSDWIN1;CRTSTG1;CRTBLR1` に `CRTSCN1` を追加する。firmwareは4つの通知がそろった場合だけ、走査線の実操作を有効にする。core切替時に能力情報を破棄し、4aのcoreへ戻した場合は走査線を再び `NOT YET` として選択対象から外す。旧bypass coreの要求値画面は従来どおり維持する。

4bのOSD2には `CRT READY - STAGE4B`、`SESSION ONLY / NO SAVE`、`CRT ENABLE`、`H BLUR`、`SCANLINE`、`APPLY`、`CLOSE`、`POS` を表示する。操作と入力遮断・解放待ち、OSD1との排他、5位置への移動は既存方式を維持する。

## 検証と確認範囲

- 走査線単体は各色成分の全256値、3強度、OFF、明るい行、共通有効flagのOFFを独立した整数式と4,096画素で照合した。
- 走査線とぼかしの全16組合せを、従来scalerから得た隣接画素と独立した係数式で照合した。
- 約5,321万画素（53,212,437）を確認し、走査線OFFの16,087,437画素は固定commitの4a実装と、両効果OFFの8,662,437画素は導入前の映像変換部と一致した。
- 43 frameで、元走査線に対応する位相と暗い行224本／720本を確認した。
- ぼかしの空間演算比較中は試験側で映像memoryの書き換えを止め、走査線単体とbypassは書き換え継続中も確認した。製品コードにゲーム停止は追加していない。
- 既存の水平ぼかし29,568画素、設定転送と65,536組のbypass、UARTと900万画素の既存映像比較も成功した。
- firmwareのCRT設定、OSD、起動経路の試験で、4bの走査線項目、旧coreへの復帰、FRAME ACK、既存操作を確認した。

firmware（221,024 byte）とNES image（4,659,294 byte）のbuildが成功した。FPGAのsetup違反・hold違反はともに0件で、report掲載の最小pulse幅にも負の余裕はなかった。clock制約は4aと同一であることを検査値で確認した。既存のPLL VCO等の警告は残る。記録は `verification/crt-stage4b/` に保存する。実機の画質・操作は未確認であり、今回の試験結果を他coreやすべてのcontrollerへ一般化しない。

## 実機試験

1. 今回のfirmwareとNES imageを対応して導入し、通常起動・映像・音声・操作を確認する。OSD2に `CRT READY - STAGE4B` が表示されることを確認する。
2. CRT ENABLEをON、H BLURをOFFにして、SCANLINEをOFF／WEAK／STANDARD／STRONGと変える。暗い行が段階的に変化し、FRAME ACKになることを確認する。
3. SCANLINEをOFFへ戻したときに4aの映像へ戻り、CRT ENABLEによる切替でも画像・文字の位置が動かないことを確認する。
4. ぼかしと走査線を併用し、OSD文字の鮮明さ、項目切替時の表示維持、ゲーム表示端、静止・動く場面での模様の安定を確認する。
5. 5位置の表示、OSD1との排他、ゲーム入力遮断と解放待ち、同じゲームでの保持と別ゲームでのOFF初期化を確認する。

2026年11月3日、対象のConsole138Kへ今回のfirmwareとNES imageを反映した。firmwareの基板側SHA-256と4 MiB全体の読み戻しを照合し、0x40000未満と0x80000以降が退避した4aと一致した。microSDは今回の58ファイルを退避してからNESだけを置換し、他の57ファイルが一致することを確認した。flash復旧用には、実機確認済み4aの検証済み全flash読み戻しをコピーして保存した。今回新たに書き込み前のflash読取を行ったという意味ではない。

導入記録は `verification/crt-stage4b/deployment.json` を参照する。通常起動後の画質・音声・操作については利用者の試験結果待ち。実機試験を終えた版を次の推奨値・ゲーム別保存・Reset to Recommendedの基準とする。

## 検討・未確認事項

暗い帯の幅と係数の視覚的な評価は実機試験で行う。gamma補正や連続的なbeam形状はこの段階では追加せず、必要性が確認された場合に別の設計として扱う。他coreの拡大位相、異なる表示機器やcontroller接続での結果は、今回の確認から推測しない。
